# APHR Event Briefings

[View the live site](https://k-mosalam.github.io/aphr-briefings/)

APHR Event Briefings is the static publication site for preliminary Automated
Post-Hazard Reconnaissance outputs. It organizes source-grounded snapshot
briefings and temporal analyses by hazard event for rapid situational awareness
and expert review.

Briefings are generated by the
[APHR evidence pipeline](https://github.com/Nutlettt/auto-vast-dev) and imported
here as web bundles. This repository owns static presentation, manifests,
build tooling, and the published product tree; it does not perform source
collection, evidence extraction, report generation, or automated Git delivery.

Cross-repository project status, accepted integration baselines, external
gates, and handoff instructions are maintained in the
[`aphr-ops` implementation plan](https://github.com/Nutlettt/aphr-ops/blob/main/docs/implementation-plan.md).
Do not duplicate that changing state in this repository.

## Repository ownership

| Path | Ownership | How to change it |
| --- | --- | --- |
| `templates/`, shared `assets/`, and `tools/` | Source-owned | Edit and review these files directly. |
| `events/<event-slug>/event.json` | Publisher-owned metadata | Let `tools/publish_product.py` add or update product entries. |
| `events/<event-slug>/products/<product-slug>/{content.html,manifest.json,assets/}` | Imported product bundle | Treat a published product slug as immutable. Publish a new slug for a new result. |
| Root, event, and product `index.html` pages | Generated | Change their template, metadata, or shared asset, then run `tools/build_site.py`. |

Do not edit generated pages or imported bundle contents to make a presentation
change. A correction to a product already present on a shared branch must use a
new product slug. Use `publish_product.py --force` only to replace an
unpublished local import before it enters shared history, never as a normal
rerun or a published-product correction.

## Local development

From the repository root, rebuild and preview the site with:

```bash
python tools/build_site.py
python -m http.server 8000
```

Then open <http://localhost:8000>.

## Publishing a product

A web bundle must contain `content.html` and `manifest.json`; it may also contain
an `assets/` directory. Publish one with:

```bash
python tools/publish_product.py \
  --bundle /path/to/bundle \
  --event-slug EVENT_SLUG \
  --product-slug PRODUCT_SLUG \
  --build
```

Run `python tools/publish_product.py --help` for optional display metadata.

This command is useful for local development and reviewed manual imports. In
the automated workflow, [`aphr-ops`](https://github.com/Nutlettt/aphr-ops)
validates the bundle and invokes this publisher inside a temporary Git worktree
created from the latest configured remote branch. The worktree is an internal
publication detail: it keeps publication changes isolated from a developer's
regular checkout and is removed after the operation.

## Publication branches

The usual frontend checkout has two remotes with deliberately different roles:

- `origin` is the personal `Nutlettt/aphr-briefings` repository;
- `origin/staging` is the automated development and acceptance target;
- `upstream` is the teacher-owned `k-mosalam/aphr-briefings` repository and
  should remain fetch-only;
- `upstream/main` is the reader-facing production branch.

A production release starts from a freshly fetched `upstream/main`, reuses the
validated bundle and publication metadata, and is proposed on a new personal
`release/*` branch through a reviewed pull request. Do not merge, cherry-pick,
or otherwise promote staging publication history as a whole: staging may
contain test-only products and has a different history from production.

The complete operational and production-release procedure is documented in
the [`aphr-ops` deployment runbook](https://github.com/Nutlettt/aphr-ops/blob/main/docs/deployment-runbook.md).

## Minimal verification

After changing presentation source or importing a product, rebuild and inspect
the exact working-tree change before committing:

```bash
python tools/build_site.py
git diff --check
git status --short
git diff --stat
git diff
```

The build should change only the source, metadata, product, and generated-page
paths expected for the task. Verify the affected pages locally before opening a
pull request. Never force-push a publication branch.
